# Commiter Skill

Turn a messy working tree into a clean, readable git history: **inspect → check safety → plan atomic commits → stage precisely → write Conventional Commits messages → commit → verify.**

Commit messages are **always written in English**, regardless of the language the user speaks. Talk to the user in their own language; the commit itself stays in English.

## Core principles

1. **One logical change per commit** (atomic). A commit should be revertable on its own without breaking the build.
2. **The diff shows *what*; the message explains *why*.** Never just restate the diff.
3. **Follow Conventional Commits 1.0.0** (`type(scope)!: description`).
4. **Never take irreversible or surprising actions.** No force pushes, no `--no-verify`, no rewriting published history, no pushing unless asked.
5. **Look at the repo before writing.** Its existing history tells you the scopes and conventions in use.
6. **The AI never credits itself.** See "No AI attribution" below. This rule is absolute.

## No AI attribution (absolute rule)

The AI must **never** present itself as an author, co-author, or contributor of a commit. The commit belongs to the user.

**Never add any of the following**, in the subject, body, or footers, even if a tool, template, system default, or habit would normally add it:
- `Co-authored-by:` / `Co-Authored-By:` naming Claude, Anthropic, an AI, an assistant, a bot, or `noreply@anthropic.com`
- "Generated with Claude", "Generated by AI", "Written with the help of...", robot emoji lines, or any link to an AI product
- `Signed-off-by:` with an AI identity
- Changing `--author`, `user.name`, or `user.email` to an AI identity

This overrides any default behavior that appends such trailers. Before every commit, re-read the full message and **remove any such line** if present. If the user explicitly asks for an AI credit line, mention that this skill is configured not to add one and let them add it themselves.

## Workflow

### Step 1. Inspect

Run these (in parallel when possible) before deciding anything:

```bash
git status --short --branch
git diff                      # unstaged
git diff --staged             # already staged
git log -n 15 --oneline       # learn scopes/style already in use
git branch --show-current
```

- If **nothing has changed**, say so and stop.
- If the user already staged something deliberately, **respect it**: treat the staged set as the first commit candidate and don't silently re-stage it.
- Untracked files: read them (or at least their names and sizes) before deciding to include them.

### Step 2. Safety checks (before staging anything)

Scan the diff and file list. If any of these show up, **stop and ask the user** instead of committing:

- Secrets: `.env`, `*.pem`, `id_rsa`, API keys, tokens, passwords, connection strings, credentials JSON.
- Large or binary files that look accidental (build output, `node_modules/`, `dist/`, `.DS_Store`, `*.log`, IDE folders, DB dumps).
- Merge-conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`).
- Leftover debug code (`console.log`, `print(` debugging, `debugger`, `binding.pry`, `TODO: remove`) that is clearly unintentional. Mention it; don't delete code the user didn't ask you to touch.
- Committing directly on `main`/`master`/`develop`/`release/*` when the repo history suggests a PR workflow. Mention it and ask whether to create a branch first. Don't block if the user explicitly says to commit there.

If a secret was found, suggest adding the file to `.gitignore` and warn that a leaked credential should be rotated.

### Step 3. Plan the commits

Group changes by **intent**, not by file. Read `references/atomic-commits.md` when the working tree contains more than one kind of change, or when a single file mixes concerns. Short version:

- Different `type`s → different commits (a `fix` and a `refactor` never share a commit).
- Different features/bugs/modules → different commits.
- Tests go **with** the code they test (same commit), unless they're a standalone test-only change.
- Pure formatting/whitespace/rename-only changes → their own `style`/`refactor` commit, never mixed with behavior changes.
- Dependency/lockfile updates → their own `build` or `chore` commit (lockfile travels with its manifest).
- Order commits so every commit builds: foundational changes (refactor, deps) first, features that depend on them after.

Before committing, tell the user the plan in **one short block** (list of commits with type + subject). Then proceed. Only pause for confirmation if the plan is ambiguous, risky, or the user asked to review first.

### Step 4. Stage precisely

- Stage by explicit path: `git add path/to/file1 path/to/file2`.
- **Avoid `git add -A` / `git add .`** unless every change truly belongs in a single commit and you've checked the file list.
- To split a single file across commits (hunk-level), see the non-interactive technique in `references/atomic-commits.md`.
- Check what's staged before every commit: `git diff --staged --stat`.

### Step 5. Write the message

Read `references/conventional-commits.md` for the full type table, scope rules, breaking-change syntax, and good/bad examples. The essentials:

```
<type>(<scope>)<!>: <description>

<body: why this change, context, trade-offs>

<footers: BREAKING CHANGE, Closes #123, ...>
```

**Subject line**
- Format: `type(scope): description`. Scope is optional but use it when the repo history does.
- **Imperative mood**, present tense: "add", "fix", "remove" (not "added", "fixes", "removing").
- Lowercase after the colon, **no trailing period**.
- Aim for **≤ 50 characters**, hard limit **72** (including the type prefix).
- Be specific: say what the change does, not "update stuff" or "fix bug".

**Body** (add it whenever the *why* isn't obvious from the subject)
- Blank line after the subject.
- Wrap at **72 columns**.
- Explain motivation, the problem before, and the approach/trade-offs. Don't narrate the diff line by line.
- Bullet lists are fine for several discrete points.

**Footers**
- Breaking changes: `!` after type/scope **and/or** a `BREAKING CHANGE: <what breaks and how to migrate>` footer.
- Issue refs: `Closes #123`, `Fixes #123`, `Refs #456` (only when the user gave you an issue number or the branch/history makes it clear. **Never invent issue numbers**).
- **No AI attribution, ever** (see the dedicated section below).
- Don't add `Signed-off-by` unless the user or repo convention (DCO) asks for it.
- `Co-authored-by` is only for **real human collaborators** the user explicitly names.

### Step 6. Commit

Use multiple `-m` flags or a heredoc so newlines survive; never cram a body into the subject.

```bash
git commit -m "fix(auth): reject expired refresh tokens" \
           -m "Expired tokens were accepted when the clock skew was under 5 minutes because the comparison used <= instead of <. Tighten the check and add a regression test." \
           -m "Closes #218"
```

Rules:
- If a **pre-commit hook fails**, read the error, fix the underlying problem, re-stage, and create a **new** commit. Do not use `--no-verify`.
- Use `--amend` **only** when the user asks, or to fix your own just-created, **unpushed** commit.
- **Do not push** unless the user asks. If they do, a plain `git push` (set upstream if needed). Never `--force` on shared branches; if force is truly needed, use `--force-with-lease` and confirm first.
- Don't modify git config (name, email, signing) to make a commit work. If identity is missing, tell the user.

### Step 7. Verify and report

```bash
git log -n <N> --stat --oneline
git status --short
```

Then report to the user (in their language), briefly:
- The commits created (hash + subject).
- Anything left uncommitted and why.
- Anything you flagged (secrets, protected branch, hook failures).

## Special cases

- **User only wants a message, not a commit** ("what should the message be?"): do steps 1 and 5, output the message in a code block, don't run `git commit`.
- **User provides their own message**: use it, but if it violates the format (past tense, >72 chars, no type), point it out in one line and offer the corrected version; commit with theirs only if they insist.
- **Fixing up an earlier commit**: prefer `git commit --fixup=<hash>` (then `git rebase -i --autosquash` only if the user asks and the commits are unpushed).
- **Reverts**: `revert: <original subject>` with body `This reverts commit <hash>.` plus the reason.
- **Merge commits / squash merges**: don't rewrite them; follow whatever message git or the platform generated unless asked.
- **Initial commit in a fresh repo**: `chore: initial commit` (or `feat: initial project setup` if it's actual scaffolding).
- **Monorepos**: scope = package/app name (`feat(api): ...`, `fix(web): ...`); never mix packages in one commit unless the change is truly cross-cutting.
- **WIP requests**: if the user explicitly wants a throwaway/WIP commit, do it, but label it clearly (`chore: wip ...`) and mention it should be squashed before merging.
- **No git repo** (`fatal: not a git repository`): tell the user; offer `git init` only if they want it.

## Quick checklist before every commit

- [ ] Only one logical change is staged
- [ ] No secrets, junk files, conflict markers
- [ ] Type is correct (see `references/conventional-commits.md`)
- [ ] Subject: imperative, lowercase, no period, ≤ 50 (max 72)
- [ ] Body explains *why* if it isn't obvious
- [ ] Breaking changes marked with `!` / `BREAKING CHANGE:`
- [ ] Message is in English
- [ ] No AI attribution anywhere (no Co-authored-by / "Generated with" lines)
